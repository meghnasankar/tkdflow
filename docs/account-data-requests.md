# Manual account data requests

Prepared 2026-11-17. This is an operator procedure, not an automatic deletion job. The public contact is support@tkdflow.com; its personal destination must never appear in tracked documents.

1. Ask the requester to contact support from their registered address. Verify control using the existing account/support channel. Never ask for a password, a reset/confirmation URL, a session token or an API key. Resolve uncertainty with the owner before exporting or deleting.
2. For a copy request, use the verified user's ID to export only that user's profile, auth-provider identity metadata, submitted school suggestions, saved forms and lesson progress (`public.member_learning`), private lesson questions with their status and moderator reply text (`public.lesson_help_questions`/`lesson_help_replies`, as returned by `my_lesson_questions`), topics, replies and reports. Never include password hashes, credentials, another member's private data or moderator-only records (for example the moderator audit trail `lesson_help_events`, moderator identities on replies, or FAQ revision history). Deliver privately to the verified account holder through an appropriate protected channel, not public GitHub or this repository.
3. For a correction, confirm the exact requested fields. The profile UI handles normal profile edits. An editable age cannot grant adult posting rights; an eligibility correction requires a separate owner-reviewed process.
4. For deletion, present the identified account and requested discussion removal to the owner. After approval, remove requested public posts/replies and associated reports before deleting the auth user. A public post's author ID becomes null on auth deletion; its stored public handle/text can remain unless removed explicitly.
5. Auth deletion cascades saved forms and lesson progress, private lesson questions with their replies and audit events, the profile, private school suggestions and reviewer/moderator roles. Enrollment eligibility has no auth foreign key because the Before User Created hook writes it before the auth row exists; explicitly remove that user's `private.account_eligibility` row in the owner-run deletion transaction. Do not add a foreign key that breaks enrollment.
   A moderator's own deletion keeps their private replies to members and any public lesson answers they wrote (the actor ID becomes null); a public answer's stored credit (`@username` or “TKDflow moderators”) remains until the entry is edited to keep or change credit, or unpublished. Public lesson answers never contain a member's private question text.
6. Reviewed public school business records can remain in the directory because they contain no member association. Do not publish/export the submitter ID or review audit identities. Expired one-use tickets can be cleared by their expiry, independently of an account request.
7. Verify deletion with counts for the identified user, then confirm completion privately. Keep only a minimal request/completion record outside the public source; do not retain an exported copy indefinitely. Provider backups and operational logs follow the relevant provider terms.

No automatic inactive-account deletion is implemented. Changes to retention periods must be reflected in the public notice before implementation. No action in this document has been executed against member records.
